# Decision Log

_Append-only. A superseded decision gets a new dated row rather than an edit —
fitting, for a project about immutable records._

## Product & approach

| Date | Decision |
|---|---|
| 2026-07-23 | **Product direction:** combined platform — metering → rating → invoicing → settlement → reconciliation — built in phases, each independently demoable. |
| 2026-07-23 | **Diverge from the standard resource model.** Ledger-first and policy-driven: what a typical billing API stores as mutable resources (Subscription, Invoice, PaymentIntent), Summa computes as projections over an append-only ledger. |
| 2026-07-23 | **AI integration principle:** AI proposes, the deterministic FP core decides. Generated artifacts (pricing policies, explanations, triage notes) must pass pure validators before anything is committed; AI never mutates state directly. |
| 2026-07-24 | **Build the ledger first** as a thin end-to-end vertical slice deployed on Azure, before designing the remaining contexts in depth. Everything depends on the ledger; the ledger depends on nothing. |
| 2026-07-28 | **Project name: Summa.** Sum types (F#), *Summa de Arithmetica* (Pacioli, 1494), and "the total." |
| 2026-07-28 | **Single public monorepo**, docs versioned alongside code, one PR per build-plan stage. |
| 2026-07-28 | **The AI layer is called Scribe.** A scribe drafts and records on behalf of an authority but has no power to decide — the name states the guardrail. (Avoids collision with Microsoft Copilot.) |

## Stack

| Date | Decision |
|---|---|
| 2026-07-23 | **Backend: F#.** Existing fluency means the learning budget goes to event sourcing and infrastructure rather than syntax; first-class Azure SDK support as a .NET language. |
| 2026-07-23 | **Frontend: TypeScript + Effect.** Chosen deliberately as new ground, on a bounded surface (read-only dashboards) where a learning curve can't compromise the core. |
| 2026-07-23 | **Cloud: Azure.** |
| 2026-07-24 | **Event store: hand-rolled on Azure Database for PostgreSQL**, behind an F# persistence port. Optimistic concurrency, polling subscriptions, and checkpointing are implemented directly — building the mechanics is the point. *Rejected:* Marten (C#-idiomatic, hides the mechanics), Equinox (excellent but imports what we want to learn), KurrentDB (no managed Azure offering). *Escape hatch:* Equinox's MessageDb backend is also Postgres, so the port allows a later swap without touching the domain. |
| 2026-07-24 | **Hosting: Azure Container Apps** — API, projection worker, and a scheduled Job for revenue recognition — with Azure Container Registry, Terraform (over Bicep, for transferability), and GitHub Actions. AKS noted as a deliberate later step; ACA already runs on Kubernetes, so containers and code carry over. |
| 2026-07-29 | **SQL migrations: forward-only, plain `.sql` files** in `db/migrations/`, applied manually via psql for now (Stage 5). A correction is a new migration, never a down script — mirrors the ledger's own append-only, reversing-entry rule rather than introducing a separate rollback mechanism. *Rejected:* DbUp/FluentMigrator/Evolve — same reasoning as the event store decision: hand-roll the mechanics rather than import them. |
| 2026-07-29 | **Migration application: hand-rolled `db/migrate.sh`**, refining the row above. A `schema_migrations(version, applied_at)` table tracks which migrations have run; the script applies each pending file inside its own transaction and skips ones already recorded, so re-running it is safe. Still no DbUp/FluentMigrator/Evolve — this only adds the tracking a plain-file approach was missing. |
| 2026-07-29 | **Postgres driver: Npgsql 10.0.3** (current stable), for the event store adapter in `Summa.Ledger.Store` (Stage 6). |
| 2026-07-29 | **Event payload serialization: FSharp.SystemTextJson 1.4.36** over `System.Text.Json`, configured to unwrap single-case and fieldless-case unions (`AccountId`, `Direction`) into plain JSON values rather than wrapped objects. |
| 2026-07-29 | **`EventStore` port: a record of functions**, not an F# `interface`. `docs/architecture.md`'s "F# port (interface)" wording is read as the architectural (hexagonal) concept, not a literal `interface`-keyword mandate — record-of-functions is more idiomatic F#. |
| 2026-07-29 | **Duplicate-idempotency-key detection: plain `INSERT` + catch Npgsql's unique-violation exception** (`SqlState="23505"`, matched to `ConstraintName`), then a follow-up `SELECT` for the existing row — not `ON CONFLICT DO UPDATE ... RETURNING (xmax = 0)`. Simpler to teach; no Postgres-internals concept required. |
| 2026-07-29 | **Query execution: Npgsql.FSharp 8.0.0** over raw Npgsql (`NpgsqlCommand`/`AddWithValue`/manual reader loop) in `PostgresEventStore.fs`, since the raw ADO.NET style was unusually imperative for F# and more DB work is expected (Stage 9's projection worker). It's a thin pipe-based wrapper, not an ORM — `PostgresException` still propagates unwrapped, so the existing exception-based duplicate detection is untouched. Both `Npgsql` and `Npgsql.FSharp` stay as direct dependencies, since `NpgsqlDataSource`/`PostgresException` are still used directly. |
| 2026-07-30 | **HTTP framework: Falco 5.2.0** for `Summa.Ledger.Api` (Stage 8), over Giraffe. Falco's `HttpHandler = HttpContext -> Task` composed with plain `>>` is the same shape ASP.NET Core minimal APIs already use — less new machinery to teach for two routes than Giraffe's `HttpFunc`/`>=>` continuation-passing layer, which earns its keep chaining many validators/middleware, not here. `Request.getJsonOptions<'T>` (verified against Falco's source) only swallows `NotSupportedException` internally, so a genuine `JsonException` on malformed JSON propagates uncaught — the hook used to give JSON-shape failures a distinct message from domain (`LedgerError`) failures. *Rejected:* Giraffe. |
| 2026-07-30 | **API integration testing: `WebApplicationFactory<Program>`** from `Microsoft.AspNetCore.Mvc.Testing` 10.0.10, in a new `Summa.Ledger.Api.Tests.Integration` project. Boots the real Falco app in-process and drives it with a real `HttpClient`, over the same real local Postgres `Summa.Ledger.Store.Tests` already uses — deliberately not the `ConfigureTestServices`/SQLite-swap pattern Microsoft's own docs show, since this repo's existing integration tests already made the opposite call (prove the real unique-constraint/idempotency mechanics, not a substitute). *Rejected:* hand-rolling a Kestrel-on-a-random-port harness. Required one F#-specific workaround: F#'s type-checker won't accept a `module` as a generic type argument, so `Program.fs`'s `module Summa.Ledger.Api.Program` (which compiles to a class) can't itself fill `WebApplicationFactory<'T>` — a marker `type Program() = class end` was added inside the module, just before `[<EntryPoint>] let main`. F# resolves the same-name collision by nesting the type inside the module's compiled class, which is why the test file opens both `Summa.Ledger.Api` (the namespace) and `Summa.Ledger.Api.Program` (the module) to bring the nested type into scope. |
| 2026-07-29 | **Dedicated `ledger` Postgres schema** for the Ledger bounded context's tables (`ledger.events`, replacing the flat `public.events`), so future contexts (Policy, Rating, Settlement) each own their own schema in the shared `summa` database rather than colliding on table names in `public`. This is bounded-context data ownership (the DDD/microservices "database per service" tradition), a deliberate choice over orthodox event-sourcing's usual answer (one shared physical store, partitioned logically by stream/category) — the two doctrines diverge here and this project picked the former, consistent with its existing per-context project namespacing. `schema_migrations` stays unqualified in `public`, since it's the migration runner's own bookkeeping, not any one context's domain data. Replaced Stage 5's `0001_events_table.sql` outright (deleted, not corrected) since nothing had been deployed yet. |
| 2026-07-30 | **Projection worker (`Summa.Ledger.Projections`, Stage 9): `Microsoft.NET.Sdk.Worker` + `Host.CreateApplicationBuilder`** (the plain Generic Host, not `WebApplicationBuilder` — no HTTP surface here) plus `Microsoft.Extensions.Hosting` 10.0.10. Confirmed by generating a real `dotnet new worker -lang F#` project rather than assuming: the Worker SDK does *not* implicitly bring in `Microsoft.Extensions.Hosting` the way `Sdk.Web` implies ASP.NET Core, and the Generic Host reads `DOTNET_ENVIRONMENT` (not `ASPNETCORE_ENVIRONMENT`) to select `appsettings.{Environment}.json`. Deliberately skips the template's default `BackgroundService`/`AddHostedService<T>`/DI-container shape — `Program.fs` constructs `NpgsqlDataSource`/`EventStore` by hand and calls `Worker.run` directly, matching `Summa.Ledger.Api/Program.fs`'s existing no-DI-container convention rather than introducing one for the first time here. The atomic balance-write + checkpoint-advance uses Npgsql.FSharp's `Sql.executeTransactionAsync` (signature confirmed by reflecting on the installed `Npgsql.FSharp.dll`, not assumed) — a list of `(query, parameter-sets)` pairs run in one transaction — over hand-rolled `NpgsqlConnection`/`BeginTransaction` plumbing. |
| 2026-07-30 | **Deferred: adopt `BackgroundService`/`IHostedService` for the projection worker** (refining the row above) once graceful SIGTERM shutdown actually matters — Stage 11 (containerize) or Stage 13 (Azure Container Apps), whichever comes first, since that's when the deployment platform starts sending SIGTERM before SIGKILL on scale-down/redeploy, and the Generic Host's hosted-service machinery is the standard way to react to that rather than hand-rolling signal handling. Not a correctness requirement — hard-kill safety is already proven unconditionally by the atomic balance-write + checkpoint-advance transaction; this is purely operational (faster/quieter redeploys) plus observability (confirmed: since .NET 6, an unhandled `BackgroundService.ExecuteAsync` exception is logged via `ILogger` before the host stops, vs. today's bare stack-trace-to-stderr with no logging at all). Deliberately not done now, since local `dotnet run` never sends SIGTERM. |
| 2026-07-30 | **Rebuild mechanism (Stage 10): `db/rebuild.sh`**, mirroring `db/migrate.sh`'s existing hand-rolled-script convention, atomically truncates `ledger.account_balances` and resets `ledger.account_balances_checkpoint.last_seq` to `0` — but deliberately does *not* restart `Summa.Ledger.Projections` itself, and rebuild is *not* exposed as an HTTP endpoint. `Worker.run` only reads the checkpoint once at startup and never re-reads it, so resetting DB state while the worker is already running has no observable effect; a full rebuild is necessarily two steps — reset stored state (the script), then restart the worker process, which replays everything via the same `loop`/`applyBatch` machinery Stage 9 already verified. Restarting stays manual: automating "kill and restart a sibling process from a script" is real added complexity for something already provably safe to do by hand, and an unauthenticated HTTP endpoint that truncates a table is a genuine risk to avoid even in a learning project. *Rejected:* `POST /rebuild` endpoint (would need either duplicating `Fold`/apply logic into `Summa.Ledger.Api` or an awkward cross-project reference to `Summa.Ledger.Projections`); a worker that watches for live checkpoint changes and auto-replays (real added complexity, not asked for by this stage). Verified end-to-end: truncated the table, ran the script, restarted the worker, confirmed via `psql` + `diff` that `account_balances` came back byte-identical to a pre-rebuild snapshot. |

## Ledger design

| Date | Decision |
|---|---|
| 2026-07-23 | **Double-entry bookkeeping.** Every transaction balances (debits = credits), so the global "all accounts sum to zero" invariant holds inductively — provable by replay, with no global lock. |
| 2026-07-23 | **Append-only.** Corrections are reversing entries, never edits or deletes. Money is stored as integer minor units; every transaction carries an idempotency key. |
| 2026-07-23 | **Revenue recognition is foundational, not a later feature.** Billing, collection, and recognition are three distinct moments that occur at different times and in different orders; a ledger that conflates them cannot be correct. |
| 2026-07-23 | **Recognition is modeled as a Performance Obligation** (ASC 606 term), created at billing. Policy answers *how much*; the Performance Obligation answers *how it becomes earned over time*. |
| 2026-07-23 | **Recognition mechanism: hybrid.** The schedule is fixed when the obligation is created; an idempotent background job posts each recognition entry as its period comes due; recognized-to-date is also computable directly, and both agree by construction. Not-yet-due recognitions are a plan, not a fact, and stay outside the ledger until due. |
| 2026-07-23 | **Tax Payable and Processing Fee Expense** added to the chart of accounts — recorded now, calculation logic deferred. Both are scheduled-settlement obligations: incurred continuously, discharged on recurring remittance dates. |
| 2026-07-23 | **Ledger accounts are internal bookkeeping categories, not connections to financial institutions.** Mapping internal accounts to external ones and proving they agree is reconciliation's job. The chart of accounts is a defined domain model (fixed types, instances parameterized per customer/currency/jurisdiction), not end-user configuration; posting rules are pure functions, not runtime config. |
| 2026-07-24 | **The Transaction is the consistency unit** — self-validating, immutable, appended to one globally-ordered log. Accounts and balances are projections. *Rejected:* one stream per account, which would require cross-stream atomic writes and break the atomic-balancing guarantee. |
| 2026-07-24 | **One Transaction = one business event.** Bill components (service, tax, fee) are entries, not separate transactions, and land in the transaction for the moment they become known. Related transactions are tied by a shared `CorrelationId`, with `CausationId` recording the immediate cause. |
| 2026-07-24 | **The ledger is unconditional** — it records any balanced transaction. Balance-dependent rules (no-negative, no-double-charge) live above it in the consumers that produce transactions. A rule needing a race-proof guarantee promotes that one account to its own stream with a version check; everything else stays a projection. |
| 2026-07-24 | **Write path:** pure `decide` → idempotent append (unique constraint on idempotency key; global identity sequence for ordering) → async projection. No version check needed on this path, since transactions are independent self-balancing facts. |
| 2026-07-28 | **Read surface for the first slice: one projection table** (`account_balances`). Trial balance and revenue-to-date are queries over it, not separate read models. As-of-date historical queries deferred. |
| 2026-07-30 | **`POST /transactions` returns `200` uniformly**, for both a fresh append and a duplicate-idempotency-key repost, with the same `{"Id": ...}` body — not `201` on first success. A `201` would misleadingly imply a resource was just created on the duplicate path too; one status code keeps both paths honest with the "duplicate is a success, not an error" rule above, instead of leaking the internal `Appended`-vs-`Duplicate` distinction into HTTP status semantics. |
| 2026-07-30 | **`account_balances.balance` uses a uniform "debits − credits" sign convention per account** (Stage 9), with no per-account-type sign flip — `AccountId` stays exactly as opaque as everywhere else in the domain; no chart-of-accounts/account-type concept was introduced. Consequence: credit-normal accounts (Deferred Revenue, Revenue) store negative — verified against the worked example: after invoice + payment + one recognition entry, Cash=12000, AR=0, Deferred Revenue=-11000, Revenue=-1000 (cents). Rationale: since `Transaction.create` already guarantees every posted transaction's debits equal its credits, summing (debits−credits) per account and then across *all* accounts is exactly zero by construction, always — making the Stage 10 trial balance a literal `SUM(balance) = 0` with no type-awareness needed anywhere, matching the "provable trial balance" pitch. *Rejected:* per-account natural-sign balances (Deferred Revenue reading as `+110`), which would require an account-type domain concept ahead of any stage actually asking for one, likely via fragile `AccountId` string-prefix inference, and would break the simple `SUM(balance)=0` trial balance property. |
